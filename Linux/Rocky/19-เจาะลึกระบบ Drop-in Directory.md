# เจาะลึกระบบ Drop-in Directory (.d) ใน Rocky Linux: สถาปัตยกรรมการจัดการคอนฟิกูเรชันระดับองค์กร

ในระบบปฏิบัติการตระกูล Enterprise Linux อย่าง Rocky Linux (รวมถึง RHEL, AlmaLinux และระบบ Linux สมัยใหม่ส่วนใหญ่) การจัดการไฟล์ตั้งค่า (Configuration Files) ได้เปลี่ยนผ่านจากการนำทุกอย่างไปรวมไว้ใน "ไฟล์เดียว" มาสู่สถาปัตยกรรมแบบกระจายศูนย์ที่เรียกว่า **Drop-in Directory** หรือไดเรกทอรีที่ลงท้ายด้วย **`.d`** (ตัวอักษร d ย่อมาจาก Directory)

สถาปัตยกรรมนี้ถูกออกแบบมาเพื่อแก้ปัญหาความซับซ้อนในการดูแลระบบ (System Administration) และเพิ่มความปลอดภัยในการอัปเดตซอฟต์แวร์

---

## 1. ทำไมถึงต้องมี Drop-in Directory? (ปัญหาที่ระบบนี้เข้ามาแก้)

ในอดีต หากคุณต้องการตั้งค่าโปรแกรม คุณต้องเข้าไปแก้ไขไฟล์หลัก (เช่น `/etc/ssh/sshd_config`) ซึ่งก่อให้เกิดปัญหาหลายประการ:

*   **วิกฤตการณ์ตอนอัปเดตระบบ (Update Conflicts):** เมื่อคุณรัน `dnf update` ระบบจัดการแพ็กเกจ (RPM) จะพยายามอัปเดตไฟล์คอนฟิกหลัก หากไฟล์นั้นถูกแก้ไขไปแล้ว ระบบจะต้องตัดสินใจว่าจะเขียนทับ (ตั้งค่าของคุณหาย) หรือสร้างไฟล์สำรองทิ้งไว้ (เช่น `.rpmnew` หรือ `.rpmsave`) ซึ่งสร้างความปวดหัวให้กับผู้ดูแลระบบที่ต้องมานั่งเทียบไฟล์ (Merge) ในภายหลัง
*   **ความเสี่ยงจาก Human Error:** การเข้าไปแก้ไขไฟล์หลักที่มีความยาวหลักร้อยหรือพันบรรทัด เสี่ยงต่อการลบผิดบรรทัด หรือทำ Syntax พัง ซึ่งอาจทำให้ Service นั้นไม่สามารถเปิดขึ้นมาได้เลย
*   **ข้อจำกัดด้าน Automation:** เครื่องมือทำ Provisioning อย่าง Ansible, Chef หรือ Puppet ทำงานได้ยากดลำบากหากต้องใช้คำสั่งค้นหาและแทนที่ข้อความ (Regex/Line replacement) ในไฟล์ขนาดใหญ่ การสั่งให้ "วางไฟล์ใหม่ลงในโฟลเดอร์" ทำได้ง่ายและเสถียรกว่ามาก

Drop-in Directory จึงเกิดมาเพื่อรับไฟล์ตั้งค่าส่วนขยาย (Extension) โดยระบบจะอ่านไฟล์หลักก่อน แล้วจึงกวาดอ่านไฟล์ทั้งหมดในโฟลเดอร์ `.d` เพื่อนำมา **"เขียนทับ (Override)"** หรือ **"ต่อท้าย (Append)"** การตั้งค่าเหล่านั้น

## 2. กลไกการทำงานของ Drop-in Directory

กลไกที่สำคัญที่สุดในการทำงานของไดเรกทอรี `.d` คือ **"ลำดับการอ่านไฟล์" (Lexicographical Order)**

เมื่อโปรแกรมเริ่มต้นทำงาน มันจะอ่านไฟล์ในโฟลเดอร์ `.d` โดยเรียงตามตัวอักษรและตัวเลข กฎพื้นฐานคือ **"ไฟล์ที่ถูกอ่านทีหลังสุด จะชนะและเขียนทับการตั้งค่าของไฟล์ที่ถูกอ่านก่อนหน้า"**

เพื่อให้การจัดการเป็นระเบียบ ผู้ดูแลระบบจึงมีธรรมเนียมปฏิบัติ (Convention) ในการตั้งชื่อไฟล์โดยใช้ตัวเลขสองหลักนำหน้า ดังนี้:
*   `10-xxx.conf` ถึง `40-xxx.conf` : สำหรับการตั้งค่าพื้นฐาน หรือการตั้งค่าเริ่มต้นจากผู้พัฒนาซอฟต์แวร์
*   `50-xxx.conf` : สำหรับการตั้งค่าทั่วไปของระบบ
*   `90-xxx.conf` ถึง `99-xxx.conf` : สำหรับการตั้งค่าแบบ Custom โดยผู้ดูแลระบบ (เพื่อให้มั่นใจว่าจะถูกอ่านเป็นลำดับสุดท้ายและเขียนทับค่าอื่นๆ ทั้งหมด)

## 3. ตัวอย่างการใช้งานจริงใน Rocky Linux พร้อมโครงสร้าง

### 3.1 การปรับแต่ง Systemd Services (`/etc/systemd/system/`)
นี่คือตัวอย่างที่ใช้บ่อยที่สุด หากคุณต้องการเปลี่ยนพอร์ตของ Nginx หรือเพิ่ม Environment Variable คุณ **ไม่ควร** ไปแก้ไขไฟล์ใน `/usr/lib/systemd/system/nginx.service` เด็ดขาด

**วิธีที่ถูกต้อง:** ใช้คำสั่ง `systemctl edit nginx`
ระบบจะสร้าง Drop-in directory ชื่อ `/etc/systemd/system/nginx.service.d/` และเปิดไฟล์ชื่อ `override.conf` ขึ้นมาให้คุณพิมพ์ส่วนที่ต้องการเขียนทับลงไป เช่น:

```ini
# /etc/systemd/system/nginx.service.d/override.conf
[Service]
LimitNOFILE=65536
Environment="CUSTOM_VAR=production"
```
เมื่อเซฟไฟล์และสั่ง `systemctl daemon-reload` การตั้งค่านี้จะผสานรวมกับไฟล์หลักทันที และจะไม่หายไปแม้จะอัปเดตแพ็กเกจ Nginx ก็ตาม

### 3.2 การจัดการ Sudoers (`/etc/sudoers.d/`)
แทนที่จะใช้ `visudo` เพื่อแก้ไขไฟล์ `/etc/sudoers` โดยตรง ซึ่งเสี่ยงต่อการตั้งค่าผิดพลาดจนพิมพ์คำสั่ง sudo ไม่ได้อีก การแยกไฟล์ตามรายชื่อกลุ่มหรือผู้ใช้คือทางออกที่ดีกว่า

**ตัวอย่าง:** ต้องการให้ผู้ใช้ชื่อ `devops` รันคำสั่ง sudo ได้โดยไม่ต้องใส่พาสเวิร์ด
สร้างไฟล์ใหม่: `visudo -f /etc/sudoers.d/90-devops-users`
```text
# /etc/sudoers.d/90-devops-users
devops ALL=(ALL) NOPASSWD: ALL
```
*หมายเหตุ: ไฟล์ใน `/etc/sudoers.d/` เป็นข้อยกเว้นที่ไม่จำเป็นต้องลงท้ายด้วย `.conf` แต่ต้องไม่มีเครื่องหมาย `~` หรือ `.` ในชื่อไฟล์*

### 3.3 แหล่งเก็บซอฟต์แวร์ DNF/Yum Repositories (`/etc/yum.repos.d/`)
Rocky Linux เก็บแหล่งดึงข้อมูลซอฟต์แวร์แยกเป็นไฟล์ๆ เช่น `rocky.repo`, `rocky-extras.repo`, `epel.repo`
หากคุณต้องการลบ หรือปิดการใช้งานแหล่งซอฟต์แวร์ใด คุณเพียงแค่ลบไฟล์นั้นทิ้ง หรือเข้าไปเปลี่ยนค่า `enabled=1` เป็น `enabled=0` ในไฟล์เฉพาะนั้น โดยไม่ต้องไปวุ่นวายกับรายการซอฟต์แวร์อื่นๆ

### 3.4 ระบบเครือข่าย NetworkManager (`/etc/NetworkManager/conf.d/`)
หากต้องการแก้ไขพฤติกรรมหลักของระบบเน็ตเวิร์ก เช่น การปิดไม่ให้ NetworkManager ไปยุ่งกับไฟล์ `/etc/resolv.conf` คุณสามารถสร้างไฟล์:
```ini
# /etc/NetworkManager/conf.d/90-dns-none.conf
[main]
dns=none
```

## 4. Best Practices สำหรับผู้ดูแลระบบ

หากคุณต้องจัดการเซิร์ฟเวอร์ Rocky Linux กฎเหล็กที่ควรยึดถือเมื่อเจอกับโปรแกรมที่รองรับ Drop-in Directory มีดังนี้:

1.  **ห้ามแตะต้องไฟล์หลักหากมีทางเลือก:** ตรวจสอบเสมอว่าโปรแกรมนั้นมีโฟลเดอร์ `.d` ให้ใช้งานหรือไม่ (มักจะมีระบุไว้ท้ายไฟล์คอนฟิกหลักในรูปแบบคำสั่ง `Include /etc/program/conf.d/*.conf`)
2.  **ตั้งชื่อให้สื่อความหมายและควบคุมลำดับ:** ใช้รูปแบบ `[ตัวเลข]-[จุดประสงค์].[นามสกุลที่ถูกต้อง]` เช่น `99-custom-security.conf` เพื่อให้คุณจำได้ว่าไฟล์นี้สร้างมาเพื่ออะไร และจะถูกประมวลผลตอนไหน
3.  **ความง่ายในการแก้ปัญหา (Troubleshooting):** หากเซิร์ฟเวอร์มีปัญหาหลังจากการปรับแต่ง คุณไม่จำเป็นต้องลบโค้ดทิ้งเพื่อทดสอบ เพียงแค่เปลี่ยนชื่อไฟล์จาก `.conf` เป็น `.conf.bak` (หรือย้ายไฟล์ออกไปที่อื่น) แล้วรีสตาร์ท Service ระบบจะหยุดอ่านไฟล์นั้นทันที ซึ่งช่วยให้ Rollback กลับไปใช้ค่าเริ่มต้นได้อย่างรวดเร็ว
